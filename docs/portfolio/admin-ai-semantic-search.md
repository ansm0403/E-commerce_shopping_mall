# 관리자 리뷰·공개 문의 의미 검색

## 해결한 문제

관리자가 “소매가 조여 움직이기 어렵다”는 불만을 찾을 때, 원문이 “팔 부분이 꽉 끼어서 움직이기 불편합니다”처럼 다른 표현을 사용할 수 있다. 최근순 조회만으로는 필요한 원문을 놓칠 수 있어 자연어 질문과 뜻이 비슷한 리뷰·공개 문의를 찾고 실제 원문 ID와 인용으로 답하도록 구현했다.

## 구현과 설계 선택

- PostgreSQL·pgvector에 768차원 임베딩을 저장했다. 기존 원본과 검색 작업을 같은 DB 트랜잭션에서 관리하고, 초기에는 정확한 코사인 검색으로 결과를 검증했다. 현재 자료 규모에서 HNSW 도입이나 대규모 성능 개선을 주장하지 않는다.
- 상품·평점·기간·문의 상태·공개 여부는 현재 원본의 SQL 조건으로 검사하고, 내용의 관련성은 임베딩으로 후보를 찾는다. 조건 적용과 의미적 관련성을 분리했다.
- 원본 버전과 작업 점유 토큰·만료를 검사한다. 임베딩 API 대기 중 원본 잠금을 유지하지 않고 저장 시 다시 검사해 수정·삭제·비밀 전환 뒤 도착한 이전 결과를 반영하지 않는다.
- 원본 저장과 외부 임베딩 처리를 분리했다. 재시도·대조·초기 색인·실패 재처리 CLI와 리뷰·문의 큐를 번갈아 처리하는 자동 워커를 제공한다.
- 연락처를 마스킹하고 비밀 문의는 임베딩 요청과 공개 검색에서 제외한다. 어시스턴트는 관리자 권한을 확인하고 실제 원문을 다시 확인한 뒤 출처를 전달받는다.
- 외부 AI의 503·시간 초과와 사용자 중단을 처리했다. 요청·턴 대기 예산과 제한된 재시도를 적용하고 SSE 연결 유지, 오류 상태 안내와 취소 후 정리를 검증했다.

## 측정한 결과와 범위

아래는 합성 자료·단일 실행의 관측이며 실제 고객 이용 성과가 아니다. 검색 지표와 최종 답변 정확도를 구분한다.

| 평가 | 자료·질문 | 최근순 기준선 | 의미 검색 |
|---|---|---|---|
| 리뷰 최종 v2 검색 | 합성 리뷰 100건, 질문 30개 중 근거 있음 20개 | Hit@5 50%, Recall@5 50% | Hit@5 100%, Recall@5 100% |
| 공개 문의 소규모 검색 | 합성 문의 27건(공개 24·비밀 3), 질문 12개 중 근거 있음 9개 | Recall@5 77.78% | Recall@5 100% |

리뷰의 DB 확인·후보 검색·최종 재확인 누적 시간은 30개 표본에서 P50 약 48.7ms·P95 약 59.5ms였다. 질문 임베딩·LLM·HTTP/SSE와 API 호출 대기 시간은 포함하지 않는다. 전체 채팅 응답 속도로 표현하지 않는다.

변경·보호 경로는 PostgreSQL·관리자 HTTP/SSE 통합 192개 검증을 기록했다. 후속 자동 워커 시연에서는 실제 Nest 스케줄러와 임베딩으로 9개 항목을 통과했다. 테스트 전체 건수는 답변 정확도의 분모로 사용하지 않는다.

## 발견한 실패와 대응

- Gemini 503과 네트워크·시간 제한을 구분해 로그에 안전한 오류 코드를 남기고, 이미 받은 텍스트나 완료한 도구를 재실행하지 않는 범위에서 재시도했다.
- 모델이 종료일을 생략하고도 요청 기간을 조회했다고 설명하거나 제목만 있는 문의에 본문이 있다고 말한 사례를 원문과 대조해 발견했다. 날짜 인자와 제목·본문·답변의 구분을 보강했다.
- 모델 보조 판정도 반환 원문을 잘못 읽거나 판정 값과 이유가 모순되는 사례가 있어, 사람의 원문 대조를 최종 판정으로 둔다.
- 후속 문의 평가에서는 빈 본문 때문에 실제 판매자 답변을 제외한 사례를 발견했다. 실제 제목·답변을 독립적으로 근거로 사용하도록 규칙을 보완했다. 작성 의도도 원문에 없으면 추정하지 않도록 명시했다.
- 문의 30문항 실행은 429로 중단됐다. 계획 30·시도 25·답변 완료 22·실패 3·미실행 5를 보존했고, 복구한 도구 인자 오류를 터미널 API 오류와 구분했다. 실패를 빼서 성공률을 높이지 않는다.

## 현재 완성도와 한계

리뷰·공개 문의 의미 검색과 사용자 화면의 수동 검증은 구현·확인했다. 자동 워커는 격리 합성 자료에서 실제 스케줄러로 확인했다. 검토 화면, 판정 JSON 저장과 검증 도구, 실제 화면의 자동 반영·영상 시연 절차를 준비했다.

리뷰 최종 30문항은 사람 판정을 완료했다. 근거 있음 18/20(90%), 근거 없음 10/10, 전체 28/30 이다. 이는 2026-10-13 측정 당시 코드의 답변이며, 실패 2건은 별점을 이유로 같은 불만을 참고로 돌린 사례와 원문에 없는 작성 의도를 덧붙인 사례다. 같은 30문항에서 LLM judge 는 사람 판정과 4건, 규칙 기반 자동 검사는 5건 어긋났다. 그래서 모델·규칙 판정은 보조로만 쓰고 사람의 원문 대조를 최종 판정으로 둔다. 문의 독립 최종 v2 30문항은 사람 판정 결과 근거 있음 12/20·근거 없음 6/10 으로 실행 전 기준(각 90%)에 미달했다. 실패 12건 중 8건은 답변 모델의 503 과부하로 답변이 생성되지 않은 실행 실패이고, 4건은 제목만 있는 미답변 문의를 근거에서 빼거나 참고로 낮춘 답변 실패다. 검색이 실행된 17문항은 모두 정답 원문을 찾았다. v2 결과로 답변 규칙(“A 이나 B” 질문, 제목만 있는 미답변 문의)과 5xx 재시도(턴당 3회·1·2·4초)를 보완하고, 상품·문의·주제가 겹치지 않는 독립 v3 30문항으로 다시 측정했다. 근거 있음 17/20(85%)·근거 없음 10/10·실행 실패 0 이었다. 근거 있음은 여전히 기준(90%) 미달이며, 실패 3건은 모두 같은 유형(제목만 있는 미답변 문의를 근거 목록에서 빼거나 낮춤)이다. 이번 실행에서는 503 이 발생하지 않아 재시도 개선의 효과는 측정하지 못했다. 남은 실패는 문의 작성 화면이 막는 빈 본문 문의에서만 나서 실사용 영향은 작다고 보고 추가 구조 변경은 보류했다. **문의 검색의 공개 통과는 주장하지 않는다.** 전체 고객 데이터 초기 색인·운영 부하·전역 쿼터 조정은 이번 소규모 평가의 범위를 넘어선다. 배송 정형 조회와 집계·결합 분석은 후속 기능이다.

## 이력서에 사용할 수 있는 문장

> 관리자 리뷰·공개 문의 의미 검색을 PostgreSQL·pgvector와 Gemini 임베딩으로 구현하고, 원본 버전·작업 점유 검증과 트랜잭션 작업 등록으로 수정·삭제·비밀 문의 변경을 검색에 반영했습니다. 고정 합성 리뷰 100건·평가 질문 30개 중 근거 있는 20문항에서 최근순 조회 대비 Hit@5와 Recall@5가 각각 50%에서 100%로 높아졌으며, 원문 인용·연락처 마스킹·외부 API 장애 처리를 검증했습니다.

이 문장은 해당 합성 자료의 검색 결과만 설명한다. 최종 답변 성공률·실제 고객 생산성·운영 처리량 수치로 바꾸지 않는다.
