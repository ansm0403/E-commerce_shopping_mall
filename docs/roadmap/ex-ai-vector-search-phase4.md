## 구현 범위

공개 문의의 제목·본문·판매자 답변을 연락처 마스킹 후 색인한다. 제목만 있는 문의도 청크와 제목 인용을 만들며, 답변만 있는 근거도 검색할 수 있다. 문의 제목은 임베딩 입력과 내용 해시에 포함되므로 제목·본문·답변 변경 모두 현재 색인을 무효화한다. 문의 출처의 `hasContent`·`hasAnswer`는 서버가 실제 마스킹 문서에서 판정한 본문·답변 존재 정보다. 답변 모델은 제목만 있는 출처에 본문을 만들어 붙이지 않고 제공된 항목만 인용한다. 원본 작성자·판매자 식별자, 벡터와 거리는 답변용 자료에 포함하지 않는다.

일반 구매자의 문의 생성, 판매자의 최초 답변, 구매자 체험 계정의 문의 생성, 문의 시드와 체험 데이터 준비·복구 경로를 작업 기록에 연결했다. 원본 변경·버전 증가·현재 작업 생성은 같은 트랜잭션에서 수행한다. 작업 기록 실패는 원본 저장도 롤백한다. 삭제는 원본 FK로 모든 프로필의 작업과 청크를 함께 제거한다.

문의 본문·제목·비밀 여부·완료된 답변을 수정하는 HTTP API나 화면은 추가하지 않았다. 내부 `InquiryService.saveSearchChange`는 호출자가 원본 잠금과 권한 검사를 마친 트랜잭션 안에서 변경 필드를 제한해 저장하고 색인 버전을 전진시킨다. 공개/비밀 전환과 답변 변경은 이 함수와 실제 PostgreSQL 통합 테스트로 검증했다. 이후 수정 API를 추가할 때도 같은 저장 경로를 사용해야 한다.

비밀 문의는 임베딩 요청과 공개 검색·coverage에서 제외한다. 공개→비밀 전환은 원본 변경 트랜잭션에서 기존 청크를 제거하고 미완료 작업을 무효화한다. 기존 색인이 있는 상태라면 작업 생성 플래그를 꺼도 비밀 전환 시 보호 정리를 수행한다. 비밀→공개 전환은 새 버전을 필요로 하며, 작업 생성이 켜져 있으면 새 작업을 기록한다. 꺼진 동안의 공개 변경은 활성화 전 대조·초기 색인으로 준비한다. 비밀 전환·삭제 중 늦게 도착한 임베딩 결과는 저장하지 않는다.

`InquiryIndexStore`·처리기·대조·CLI는 리뷰와 원본 종류를 분리한다. 현재 프로필·원본 버전·공개 여부·작업 점유 토큰과 만료를 확인한 뒤 청크 전체와 완료 기록을 커밋한다. 재사용은 같은 제목·본문·답변의 해시뿐 아니라 현재 저장 청크의 버전·텍스트·개수·벡터와 완료 기록까지 일치해야 한다. 임베딩 전에 공개 여부를 다시 검사하며 외부 요청을 기다리는 동안 원본 행 잠금을 유지하지 않는다.

`SemanticSearchService.searchInquiries`와 `summarize_inquiries(query)`를 관리자 채팅에 연결했다. query가 없으면 기존 조건 조회를 유지하고, query가 있으면 현재 공개 문의의 정확한 코사인 거리 상위 10청크에서 기본 5·최대 10개 원본을 반환한다. 원본당 인용은 최대 2개, 인용 문맥은 12,000 Unicode 코드 포인트까지다. 제목도 마스킹한 인용에 포함한다. 준비된 후보는 실제 질문의 근거인지 답변 모델이 확인해야 하며 유사도 임계값이나 재순위화 모델은 추가하지 않았다.

상품·카테고리·현재 문의 상태(`waiting`/`answered`)·명시한 KST 날짜 범위를 적용한다. 답변 문자열 유무로 상태를 추정하지 않고 원본의 현재 상태를 사용한다. 빈 상품·카테고리 범위를 전체로 확대하지 않는다. 기간을 생략하면 전체 기간이며 자동으로 최근 1개월을 추가하지 않는다. KST 종료일의 마지막 마이크로초까지 포함한다.

현재 버전의 완료 작업·프로필·청크 건전성을 검사하고, 반환 직전 별도 읽기 스냅샷에서 제목·본문·답변 해시와 현재 공개 여부·조건을 다시 확인한다. 검색 도중 삭제·비밀 전환·상품/카테고리/상태 변경·새 버전 완료가 일어나면 오래된 인용을 제외한다. 보장 기준은 마지막 DB 확인 시점이며 답변 생성 중 이후의 변경까지 잠금으로 고정하지 않는다.

결과는 리뷰와 같은 `status/mode/scope/data/coverage/error` 구조다. `no_data`, `no_candidates`, `indexing`, `unavailable`을 구분하고, 일부만 준비된 검색은 partial을 기록한다. 문의 검색 플래그가 꺼져 있으면 모델의 query 스키마를 숨기고 직접 의미 검색 호출은 `unsupported`로 반환한다. 리뷰 검색 플래그와 독립적으로 사용할 수 있다. 서버 인증 컨텍스트·안전한 오류·마스킹·중단 신호·SSE heartbeat는 기존 채팅 경로를 그대로 사용한다.

## 자동 검증

커밋 전 재검사에서는 로컬 `.env`의 문의 작업 생성 플래그가 켜져 있을 때, 비활성 상태를 가정한 단위 테스트 3개가 환경변수를 읽어 실패했다. 테스트 설정에 작업 생성 플래그와 프로필의 명시적 기본값을 넣어 격리한 뒤 전체 단위 **831/831, 55개 스위트**와 백엔드·검색 평가 타입 검사를 다시 통과했다. 원본 저장·검색의 운영 코드는 변경하지 않았다.

현재 기록은 다음 실행을 확인했다. 전체 백엔드 단위 테스트는 **831/831, 55개 스위트**를 통과했고 백엔드·검색 평가 타입 검사, lint와 개발 빌드도 통과했다. 최초 채팅 파일럿의 답변 보완 후에도 전체 단위 831개, 문의 검색 통합 41개와 관리자 HTTP/SSE 통합 15개, 타입·lint·개발 빌드를 재실행해 통과했다. lint에는 기존 경고가 있으며 개발 빌드의 기존 Nx lockfile 축소 메시지와 루트 lockfile fallback도 유지된다.

| 검증 | 결과 | 사용하는 경로 |
|---|---:|---|
| 문의 색인·원본 저장 PostgreSQL 통합 | 44/44 | 실제 DB, 임베딩 대역 |
| 공개 문의 검색 PostgreSQL 통합 | 41/41 | 실제 DB, 질문 임베딩 대역 |
| 관리자 인증 HTTP/SSE 통합 | 15/15 | 실제 Nest 가드·HTTP·DB, LLM/임베딩 대역. 기존 리뷰 사례 포함 |

기존 기반 DB **7/7**, 리뷰 색인 **49/49**, 리뷰 검색 **36/36**도 함께 재실행했다. 해당 시점의 6개 SQL/HTTP 통합 스위트 합계는 **192/192(7+49+36+44+41+15)**다. 문의의 새 저장·검색 기능 때문에 이전 리뷰 보호 동작이 바뀌지 않았는지도 확인했다.

색인 검증에는 공개/비밀 전환, 일반 생성·최초 답변, 체험 저장, 내용 변경·재사용, 오래된 결과, 점유 만료, 저장 롤백, 비활성 중 비밀 정리, 삭제 FK, 대조와 실패 처리가 포함된다. 검색 검증에는 제목만/답변만 있는 근거, 연락처, 비밀 문의의 coverage 제외, 현재 상태·상품·카테고리·날짜 조건, 미반영/실패 구분, 질문 임베딩 중 및 순위 결정 후 변경, 직접 SQL 변경·손상, 권한·취소가 포함된다. HTTP 검증은 관리자 컨텍스트·채팅 연결·마스킹·플래그·응답 계약을 확인하며 구매자·셀러 화면의 실제 조작을 대신하지 않는다.

자동 DB 검증은 `shopping_mall_search_probe`의 실행별 임의 스키마를 만들고 끝나면 제거한다. 사용자 수동 DB의 문의를 일괄 색인하거나 고객 원문을 외부 API로 전송하지 않는다.

## 평가 자료와 측정 범위

[문의 fixture](../../backend/eval/search/inquiry-fixture.ts)는 개선용 `inquiries-improvement-v1`과 주제를 공유하지 않는 별도 소규모 검증용 `inquiries-final-small-v1`을 제공한다. 각 자료는 **합성 문의 27건(공개 24·비밀 3), 질문 12개(근거 있음 9·없음 3)**다. 실제 고객 원문은 0건이다. 제목 근거·본문 근거·판매자 답변, 반대 경험, 상태·기간 조건과 근거 없음 질문을 포함한다. 모든 조건 범위의 관련 원본 ID와 판정 이유를 고정했다.

별도 검증용의 실제 임베딩 실행 전에 기준을 **Hit@5 95% 이상·Recall@5 90% 이상, 비밀 원본·원문 연락처 노출 0건**으로 고정했다. 같은 기준을 [fixture 코드](../../backend/eval/search/inquiry-fixture.ts)에 보존한다. 결과를 본 뒤 기준을 낮추지 않는다. 합성 질문 12개는 설계의 최종 답변 30문항을 대신하지 않는다.

비교 A는 같은 공개 여부·상품·상태·날짜 조건의 최근순 원본 5개, B는 고정 검색 문구를 서비스에 직접 전달한 의미 검색이다. 근거 없음 질문에는 임계값 없이 무관한 후보가 반환될 수 있으므로, 서버 결과를 곧바로 근거 없음 답변 성공으로 채점하지 않는다. 실제 답변 생성과 사람 판정은 별도 작업이다.

기본 mock 실행은 개선용과 별도 검증용 각각 **12/12 완료**, 외부 요청 **0회**, 확인한 비밀 원본·원문 연락처 노출과 보호된 입력 전송 **0건**이었다. [개선용 mock 결과](../../backend/eval/results/search-inquiry-retrieval-mock-improvement-2026-10-13T18-53-39-529Z.json)와 [별도 검증용 mock 결과](../../backend/eval/results/search-inquiry-retrieval-mock-final-small-2026-10-13T18-54-00-606Z.json)를 보존한다. 결정적 주제 벡터로 확인한 SQL·색인·인용 경로 검증이므로 mock의 Hit/Recall을 실제 임베딩 검색 품질로 표현하지 않는다.

별도 소규모 자료의 [실제 임베딩 검색 결과](../../backend/eval/results/search-inquiry-retrieval-live-final-small-2026-10-13T18-57-18-160Z.json)는 **계획 12·실행 12·API 오류 0**이었다. 공개 문의 24건의 24청크를 준비했고, 비밀 3건은 임베딩 입력에서 제외했다. `gemini-embedding-2` 768차원의 실제 외부 요청은 **25회(문서 입력 19종·질문 입력 6종)**, 동일 입력의 평가 캐시 조회는 문서 5회·질문 6회였다. 입력 토큰 값은 API가 제공하지 않아 null이다. 확인한 비밀 원본 반환·원문 연락처 노출·보호된 입력 전송은 0건이었다.

| 방식 | 근거 있음 분모 | Hit@5 | Recall@5 | Precision@5 |
|---|---:|---:|---:|---:|
| 같은 조건의 최근순 5개 | 9 | 100% | 77.78% | 26.67% |
| 정확한 코사인 의미 검색 | 9 | 100% | 100% | 40% |

3개의 근거 없음 질문은 위 지표의 분모에서 제외했다. 실제 임베딩의 Recall 차이는 이 고정 합성 자료에서 **22.22%p**이며, 실제 고객 이용 성과나 답변 정확도의 개선으로 해석하지 않는다. 무필터·답변 완료·답변 대기 질문의 정답 수가 각각 3·2·1개여서 평균 Precision@5 상한은 40%다. 같은 검색 문구를 상태 필터만 바꿔 반복한 질문도 포함하며 서로 독립적인 불만 주제 12개로 표현하지 않는다.

실측은 합성 자료·단일 반복·소규모 검색 검증이다. 답변 LLM을 실행한 결과가 아니므로 근거 없음 응답 성공률, 최종 답변 성공률, HTTP 지연이나 운영 처리량을 보고하지 않는다. 원본 결과 파일에는 실행 시점 코드 해시와 실제 입력 준비 시간·검색 시간·캐시·API 요청량을 보존했다. 이후 코드 보완은 이 실행의 원본 결과를 덮어쓰지 않고 후속 검증으로 기록한다.

검색 도중 비밀 전환된 원본을 최종 후보·제외 건수에서도 제외하는 보완 후 [동일 자료 재검증](../../backend/eval/results/search-inquiry-retrieval-live-final-small-2026-10-13T19-03-40-103Z.json)은 **12/12 실행·API 오류 0**, 기존 실제 벡터 캐시로 외부 임베딩 요청 **0회**, 같은 검색 지표를 확인했다. 같은 12문항의 재실행이므로 독립 질문 수를 늘려 집계하지 않는다. 위 표의 최초 실제 임베딩 측정과 두 실행의 원본 파일은 각각 보존한다.

## 실제 채팅 파일럿에서 발견한 답변 실패

최초 [실제 Gemini 채팅 파일럿](../../backend/eval/results/search-inquiry-assistant-pilot-2026-10-13T19-05-39-638Z.json)은 제목 근거·근거 없음의 합성 질문 **계획 2·실행 2**, 실제 LLM SDK 요청 **4회**, SDK/최종 API 오류 **0건**, 새 질문 임베딩 **2회**였다. 캐시된 실제 문서 벡터로 격리 DB를 준비하고 자연어 질문→실제 도구·인자 선택→검색→답변을 실행했다. 비밀 원본·원문 연락처의 확인한 노출은 0건이었다.

실행은 끝났지만 요청 조건과 원문 충실성에 다음 실패가 있었다.

- 두 질문 모두 도구에 `startDate=2026-10-01`만 전달하고 명시한 `endDate=2026-10-13`을 생략했다. `expectedScopeUsed`는 **두 건 모두 false**인데 답변은 13일까지 조회한 것처럼 표현했다.
- 제목만 있고 본문이 빈 문의 **#4001**을 답변에서 “본문은 제목과 동일한 내용”이라고 설명했다. 제공하지 않은 본문을 만들어 낸 것이다.
- 문의 **#4004**의 실제 본문은 걱정했던 문제가 **없었다**는 내용인데 어깨 통증·교환 문제의 근거로 함께 인용했다. 관련 단어가 포함된 반대 경험을 실제 불만으로 해석했다.

근거 없음 질문은 무게 자동 기록 기능의 고장 근거가 없다고 답했지만 종료일을 적용하지 않았으므로 질문 전체의 통과로 집계하지 않는다. API 오류 0건·출처 ID 존재만으로 답변 성공률을 계산하지 않는다. [원문·실제 도구·답변을 보존한 사람 검토 문서](../../backend/eval/results/search-inquiry-assistant-human-review-2026-10-13T19-05-39-638Z.md)의 두 판정은 현재 **pending**이며 위 내용은 에이전트가 원문과 비교해 발견한 문제다. 사람 판정을 대신 완료한 것으로 바꾸지 않았다.

이 결과를 보고 문의의 시작일·종료일 스키마 설명을 분리하고 양끝을 명시한 질문의 종료일을 빠뜨리지 않도록 안내했다. 출처에 `hasContent`·`hasAnswer`를 추가하고 제목만 있는 문의의 본문 생성 금지, 실제 문제 없음·걱정·가정의 구분과 반대 경험 처리 규칙을 보강했다. 최초 두 문항은 이후 답변 개선용으로 전환하며 원본 답변·실패 기록을 덮어쓰지 않는다. 보완 확인에는 다른 상품·문의 ID·주제·종료일과 기간 밖 함정 원문을 가진 별도 2문항을 사용했다.

## 별도 자료의 소규모 채팅 확인

[별도 자료](../../backend/eval/search/inquiry-pilot-confirmation-fixture.ts) `inquiries-assistant-confirmation-v1`은 합성 문의 **10건(공개 8·비밀 2), 질문 2개**다. 이전 파일럿과 상품·문의 ID·주제가 다르고 기간은 **2026-10-01~2026-10-12**로 고정했다. 기간 밖의 같은 불만 원문을 함께 준비해 종료일을 실제로 적용하는지 확인한다.

첫 [2문항 확인 실행](../../backend/eval/results/search-inquiry-assistant-pilot-2026-10-13T19-14-33-396Z.json)은 **계획 2·실행 2·최종 답변 완료 1·최종 API 오류 1**이었다. SDK 요청 **6회**, 관측한 SDK 실패 **3회**는 모두 503이며 복구된 실패도 포함한다. 새 실제 임베딩 요청은 **10회(문서 8·질문 2)**, 확인한 비밀·연락처 노출은 0건이었다.

- 제목 근거 질문은 SDK 요청 3회 중 503 1회를 재시도로 복구했다. 도구에 상품 501, `startDate=2026-10-01`, `endDate=2026-10-12`, `status=waiting`을 정확히 전달했다. 기간 밖 문의 #5004를 제외하고 #5001 제목을 인용했으며, 본문이 없다고 설명했다. #5002의 “실제로 받은 상자는 마르고 멀쩡했습니다”를 실제 불만에서 제외했다고 명시했다. 이 내용은 에이전트가 실제 인자·자료·답변을 대조한 관측이다.
- 근거 없음 질문도 상품 502와 양끝 날짜를 정확히 전달했고, 기간 밖 곰팡이 문의 #5014를 반환하지 않았다. 검색 후 답변 요청이 503으로 실패하고 1회 재시도도 503으로 끝나 **최종 답변은 없다**. 이를 올바른 근거 없음 답변이나 2/2 통과로 집계하지 않는다.

이후 실패한 근거 없음 **한 문항만** [별도 부분 재검증](../../backend/eval/results/search-inquiry-assistant-pilot-2026-10-13T19-15-44-996Z.json)했다. **선택 1·실행 1·답변 완료 1·최종 API 오류 0**, SDK 요청 **3회** 중 503 1회가 복구됐다. 기존 실제 벡터 캐시를 사용해 새 임베딩 요청은 **0회**였다. 시작일·종료일을 정확히 전달하고 임의의 상태 조건을 추가하지 않았으며, 반환 원문은 #5011·#5012·#5013이고 기간 밖 #5014는 제외됐다. 답변은 가져온 자료에서 곰팡이 불만 근거를 찾지 못했다고 설명했고 잘못된 불만 인용은 관측하지 않았다.

최초 2문항 실행의 실패와 후속 1문항 부분 결과를 합쳐 단일 실행 2/2 성공으로 표현하지 않는다. [첫 확인의 사람 검토](../../backend/eval/results/search-inquiry-assistant-human-review-2026-10-13T19-14-33-396Z.md)와 [부분 재검증의 사람 검토](../../backend/eval/results/search-inquiry-assistant-human-review-2026-10-13T19-15-44-996Z.md)는 **pending**을 유지한다. 원문 충실성·조건·무관한 후보의 해석에 대한 위 관측은 에이전트 확인이며 확정 사람 판정이나 최종 답변 30문항의 성공률이 아니다. 실제 사용자 화면 확인도 별도 남아 있다.

이번 단계의 위 외부 측정에서 실제 임베딩 요청은 합계 **37회(검색 25 + 최초 채팅 2 + 별도 확인 10 + 부분 재검증 0)**, 실제 답변 LLM SDK 요청은 **13회(최초 4 + 별도 확인 6 + 부분 재검증 3)**다. 실패·복구 요청도 SDK 횟수에 포함하며 실패 요청의 토큰 사용량이 없으면 0으로 가정하지 않는다. 캐시 기반 검색 재검증은 새 임베딩 요청을 추가하지 않았다.

## 재현 명령

프로젝트 루트의 PowerShell 터미널에서 실행한다. DB 통합 검증은 검색 전용 PostgreSQL이 필요하다.

```powershell
yarn nx run '@shopping-mall/backend:search:db:up'
yarn nx run '@shopping-mall/backend:search:inquiry:index:verify'
yarn nx run '@shopping-mall/backend:search:inquiry:query:verify'
yarn nx run '@shopping-mall/backend:search:chat:verify'
yarn nx run-many -t typecheck search:typecheck -p '@shopping-mall/backend'
yarn nx run '@shopping-mall/backend:test' --runInBand
yarn nx run '@shopping-mall/backend:search:inquiry:query:eval' --embedding=mock --split=improvement
yarn nx run '@shopping-mall/backend:search:inquiry:query:eval' --embedding=mock --split=final
```

실제 임베딩 측정은 `--embedding=live`를 명시한다. API 키는 `backend/.env`를 읽지만 원본은 격리 스키마의 합성 문의만 사용한다. 평가에서만 동일 합성 입력의 실제 벡터를 캐시하며 운영 색인은 원본 간 벡터를 공유하지 않는다. 캐시 조회 시간과 원래 외부 API 준비 시간을 구분한다. 모델 평가 프로세스는 동시에 실행하지 않는다.

```powershell
yarn nx run '@shopping-mall/backend:search:inquiry:query:eval' --embedding=live --split=improvement
yarn nx run '@shopping-mall/backend:search:inquiry:query:eval' --embedding=live --split=final
```

채팅 파일럿은 `--live`가 없으면 계획만 출력하며 DB·외부 API 요청을 실행하지 않는다. 아래 실제 실행은 격리 DB의 합성 문의만 사용하고 실패하면 이후 문항을 중단한다. 한 문항만 다시 실행한 경우 부분 결과로 보존한다.

```powershell
yarn nx run '@shopping-mall/backend:search:inquiry:assistant:pilot' --fixture=confirmation
yarn nx run '@shopping-mall/backend:search:inquiry:assistant:pilot' --live --fixture=confirmation
yarn nx run '@shopping-mall/backend:search:inquiry:assistant:pilot' --live --fixture=confirmation --cases=absent
```

문의 운영 CLI는 리뷰 CLI와 별도다. `--apply`가 없으면 안내만 출력하고 DB에 연결하지 않는다. 적용 명령은 `backend/.env`의 DB를 사용한다. 수동 확인은 [화면 검증](./ex-ai-vector-search-phase4-manual-test.md)의 새 문의만 대상으로 진행하며 초기 전체 색인은 공개 준비 단계에서 별도로 수행한다.

```powershell
yarn nx run '@shopping-mall/backend:search:inquiry:backfill'
yarn nx run '@shopping-mall/backend:search:inquiry:work' --apply --limit=1
yarn nx run '@shopping-mall/backend:search:inquiry:reconcile'
yarn nx run '@shopping-mall/backend:search:inquiry:retry-failed' --apply --inquiry-id=123
yarn nx run '@shopping-mall/backend:search:inquiry:cleanup'
```

## 공개 전 남은 확인

사용자는 [문의 화면 검증](./ex-ai-vector-search-phase4-manual-test.md)의 1~6번을 완료했다고 보고했다. 일반·체험 경로의 구분과 공유 로그의 범위는 해당 문서에 기록한다. 아래 기존 합성 자료의 평가·사람 검토와 전체 초기 색인 조건은 이 화면 확인과 별개로 유지한다.

최종 자동 검사·실제 요청·실패와 부분 재검증·현재 소스 해시는 [검증 요약](../../backend/eval/results/search-phase4-verification-2026-10-14.json)에 기록했다. [백엔드 단위 원본](../../backend/eval/results/search-phase4-unit-2026-10-14.json)과 [최초 단위 설정 실패](../../backend/eval/results/search-phase4-unit-initial-2026-10-14.json)도 보존한다. 단위 설정 실패는 불필요한 ScheduleModule을 DI 식별 테스트에 넣어 발생한 Nest 패키지 중복 문제였고 테스트 설정을 고친 뒤 전체 831개를 재검증했다.

문의 검색 플래그의 기본값은 false다. 기존 공개 문의의 초기 색인·미해결 실패 확인, 일반/체험 화면 검증, 자연어 도구·조건 선택부터 최종 답변까지의 별도 평가와 사람 대조가 공개 조건이다. 최초 파일럿의 날짜·원문 충실성 실패는 보완하고 별도 자료에서 확인했으며, 그 확인의 503 실패와 부분 재검증도 각각 보존했다. 아직 문의의 최종 답변 30개를 생성·판정한 기록은 없으며 확정 답변 성공률을 보고하지 않는다.

리뷰의 [최종 답변 30개 사람 검토](../../backend/eval/results/search-human-review-2026-10-13T11-17-44-591Z.md)도 기존 미완료 항목으로 유지한다. 문의 구현·단위/DB 통과가 리뷰의 사람 검토나 전체 초기 색인 완료를 뜻하지 않는다. 설계의 정형 배송 조회와 복합 도구 실행은 다음 단계다.
