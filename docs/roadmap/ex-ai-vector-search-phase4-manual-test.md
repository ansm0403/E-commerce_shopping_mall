# 공개 문의 의미 검색의 실제 화면 검증

2026-10-14 KST. [4단계 구현](./ex-ai-vector-search-phase4.md)의 문의 화면 검증 절차다. 사용자는 아래 1~6번 화면 검증을 완료했다고 보고했다. 공유한 대화에서는 상품 253의 문의 #148에 대한 색인 대기·마스킹한 인용·답변 상태·명시적 하루 조회와 비밀 문의 제외, 상품 271의 미답변 문의 삭제 후 근거 없음 응답을 확인했다. 작성 전날 제외와 취소·복원은 별도 대화 로그 없이 사용자 완료 보고로 기록하며 자동 통합 검증과 구분한다. 이미 검색 마이그레이션을 적용한 수동 테스트 DB와 기존 API 키 설정을 사용한다.

격리 DB의 소규모 실제 채팅에서는 양끝 날짜 전달·제목만 있는 원본·반대 경험 제외를 보완해 확인했다. 2문항 실행 중 1문항은 Gemini 503으로 답변을 완료하지 못했고 그 문항만 따로 재검증했다. 이 결과는 아래 실제 계정·화면의 검증 완료를 뜻하지 않는다.

## 환경과 계정

`backend/.env`에 아래 값을 설정한다. worker를 끄면 직접 명령을 실행하기 전 색인 대기 상태를 확인할 수 있다.

```dotenv
AI_SEARCH_INQUIRY_INDEX_ENABLED=true
AI_SEARCH_INQUIRIES_ENABLED=true
AI_SEARCH_WORKER_ENABLED=false
AI_SEARCH_REVIEWS_ENABLED=false
```

리뷰 작업도 독립적으로 끄려면 `AI_SEARCH_REVIEW_INDEX_ENABLED=false`로 설정한다. 문의 검증 때문에 DB 연결 값을 바꾸거나 기존 DB를 재생성할 필요는 없다. 현재 백엔드 터미널에서 `Ctrl+C`로 중지한 뒤 프로젝트 루트에서 다시 실행하고 프론트를 새로고침한다.

```powershell
yarn nx run '@shopping-mall/backend:serve'
```

문의 작성은 일반 구매자 계정, 답변은 **그 상품의 셀러 계정**, 검색은 관리자 계정으로 진행한다. 계정별 다른 브라우저 세션을 사용하면 전환하기 편하다. 테스트 상품은 해당 셀러로 답변할 수 있는 식품 상품을 고른다. 이전 상품 **577 / 맛있는 소보로빵 (238g)**도 그 상품 셀러로 접근할 수 있을 때 사용할 수 있다. 아래 `N`은 실제 **상품 ID**, `I`는 새로 생성한 **문의 ID**로 바꾼다. 리뷰 ID 1874를 문의 ID로 사용하지 않는다.

구매자 체험 계정은 허용된 체험 상품에 문의를 작성할 수 있다. 셀러 체험 계정은 정해진 구매자 체험 계정의 허용된 문의만 답변할 수 있고 체험 계정은 문의 삭제가 금지된다. 삭제까지 확인하려면 일반 구매자 계정으로 작성한 **별도의 미답변 문의**가 필요하다.

검색 질문은 각 시나리오를 새 대화에서 시작한다. 다른 공개 문의가 같은 상품에 남아 있으면 전체 상품 결과가 아닌 기록한 문의 ID·인용의 포함 여부를 비교한다.

## 1. 공개 문의 작성 후 색인 대기

상품 `/products/N`의 문의 탭에서 공개 문의 A를 작성한다.

- 제목: `빵이 너무 단단한데 부드럽게 먹는 방법이 있나요?`
- 본문: `빵이 딱딱해서 씹기 어렵습니다. 부드럽게 먹는 방법을 알려주세요. 테스트 연락처 fixture@example.com, 010-1234-5678입니다.`
- 비밀 문의: 해제

새 문의 ID `I_A`를 기록한다. 화면에 ID가 없다면 브라우저 개발자 도구의 Network에서 `POST /inquiries` 응답의 `id`를 확인한다. 상품 주소의 숫자는 문의 ID가 아니다.

아직 처리 명령을 실행하지 않은 상태에서 관리자 어시스턴트에 질문한다.

> 상품 N의 전체 기간 공개 문의에서 빵이 단단해서 씹기 어렵다는 내용을 의미 검색으로 찾아줘. 문의 ID와 원문을 인용해줘. 기간 제한을 추가하지 말아줘.

새 문의만 있는 범위라면 색인 반영 중(`indexing`) 안내가 기대 결과다. 다른 준비된 공개 문의가 있으면 일부 자료 기준임을 밝혀야 하며 아직 반영되지 않은 A를 완료된 인용으로 반환하면 안 된다.

## 2. 수동 처리와 마스킹한 인용

백엔드 서버는 계속 실행해 두고 **별도의 프로젝트 루트 PowerShell 터미널**에서 전체 명령을 실행한다.

```powershell
yarn nx run '@shopping-mall/backend:search:inquiry:work' --apply --limit=1
```

출력의 `inquiryId`가 `I_A`이고 `status`가 `done`인지 확인한다. `--limit=1`은 대기 작업 하나를 처리하는 값이다. 더 오래된 문의 작업이 먼저 처리되었다면 새 문의의 ID가 나올 때까지 같은 명령을 실행한다. `idle`인데 새 문의가 반영되지 않았다면 문의 작성 시점의 작업 생성 플래그와 재시작 여부를 확인한다.

새 대화에서 1번 질문을 다시 한다. 기대 결과는 **문의 #I_A**와 실제 제목·본문의 인용이다. 원문 이메일·전화번호는 응답에 그대로 나오면 안 되며 마스킹한 문자열은 허용한다. 임의의 최근 1개월 조건을 추가하면 안 된다.

근거 없음도 별도 확인한다.

> 상품 N의 전체 기간 공개 문의에서 빵에 곰팡이가 생겼다는 불만을 의미 검색으로 찾아줘. 문의 ID와 원문을 인용해줘.

다른 문의에 곰팡이 근거가 없다면 “가져온 자료에서는 관련 근거를 찾지 못했다”고 답해야 한다. 딱딱한 빵 문의를 곰팡이 근거로 인용하면 실패다. 기존 공개 문의에 실제 곰팡이 내용이 있다면 그 원문과 ID를 확인하며 무조건 근거 없음으로 판단하지 않는다.

## 3. 최초 답변 저장과 현재 상태

해당 상품 셀러로 `/seller/inquiries`에서 문의 A에 최초 답변을 작성한다.

> 전자레인지에 10초 정도 데우면 부드러워집니다. 오래 데우면 다시 단단해질 수 있습니다. 테스트 연락처 fixture-answer@example.com입니다.

답변 저장 후에는 현재 상태가 `answered`다. 새 대화에서 아래 질문을 먼저 한다.

> 상품 N의 전체 기간 답변 대기 중인 공개 문의에서 빵이 딱딱해서 씹기 어렵다는 내용을 의미 검색으로 찾아줘. 적용한 문의 상태 조건도 알려줘.

기대 결과: **답변 완료된 A는 `waiting` 결과에서 제외**된다. 다른 미답변 문의가 없다면 조건에 맞는 데이터가 없다고 답한다. 답변 완료 조건의 검색은 새 버전 색인이 반영 중이라고 안내할 수 있다. 이전 인용을 최신 답변으로 꾸며내면 안 된다.

2번의 수동 처리 명령을 다시 실행한다. `inquiryId=I_A`, 다음 `version`, `status=done`을 확인한 뒤 새 대화에서 질문한다.

> 상품 N의 전체 기간 답변 완료된 공개 문의에서 빵을 부드럽게 먹는 방법을 의미 검색으로 찾아줘. 문의 ID와 판매자 답변 원문을 인용해줘.

기대 결과: **문의 #I_A**, “10초 정도 데우면 부드러워집니다”라는 실제 답변 근거를 인용한다. 답변의 원문 이메일은 그대로 나오면 안 된다. 모델이 질문하지 않은 구매자 의도나 추가 조리 방법을 근거 없이 만들면 실패다.

현재 UI와 API는 최초 답변만 지원한다. 완료된 답변 수정·문의 본문 수정·공개/비밀 전환을 화면에서 수행하는 단계는 없다. 이 변경들은 내부 저장 함수·실제 SQL 통합 테스트로 확인했으며 수동 검증 때문에 임의 수정 API를 가정하지 않는다.

## 4. 비밀 문의 제외

같은 상품에 별도 비밀 문의 C를 작성하고 `I_C`를 기록한다. 공개 문의와 구별하기 위해 다음 내용을 사용한다.

- 제목: `비밀검증 문구: 포장 봉투가 찢어져 있었습니다`
- 본문: `비밀검증 문구입니다. 포장 봉투가 찢어져 내용물이 바닥으로 떨어졌습니다.`
- 비밀 문의: 선택

관리자 새 대화에서 질문한다.

> 상품 N의 전체 기간 문의에서 비밀검증 문구나 봉투가 찢어져 내용물이 떨어졌다는 내용을 의미 검색으로 찾아줘. 문의 ID와 원문을 인용해줘.

기대 결과: **비밀 문의 #I_C와 비밀 본문을 반환하지 않는다.** 비밀 문의 때문에 공개 색인이 대기 중이라고 안내하거나 공개 원본 수에 포함하면 안 된다. 비밀 문의는 처리할 작업을 만들지 않으므로 이 사례 때문에 수동 worker 명령을 실행할 필요가 없다. 공개 자료의 다른 파손 문의가 반환되면 그 ID가 C가 아닌지 대조한다.

## 5. 명시적 날짜와 취소

날짜 조건은 **문의 작성일** 기준이며, 판매자 답변을 저장한 날짜가 아니다. 문의 화면에서 A의 실제 작성일(KST)을 확인한다. 앞의 날짜는 시작일, 뒤의 날짜는 종료일이다. 이 포함 검증에서는 **두 곳 모두 A의 작성일과 같은 날짜**를 넣어 그 하루를 조회한다.

> 상품 N의 YYYY-MM-DD부터 YYYY-MM-DD까지 답변 완료된 공개 문의에서 빵을 부드럽게 먹는 방법을 의미 검색으로 찾아줘. 문의 ID와 답변을 인용하고 적용한 기간을 알려줘.

예를 들어 상품 253의 문의 #148을 **2026-10-14에 작성했다면** 다음과 같이 질문한다. 실제 작성일이 다르면 두 날짜를 모두 그 작성일로 바꾼다.

> 상품 253의 2026-10-14부터 2026-10-14까지 답변 완료된 공개 문의에서 빵을 부드럽게 먹는 방법을 의미 검색으로 찾아줘. 문의 ID와 판매자 답변 원문을 인용하고 적용한 기간을 알려줘.

기대 결과: 양끝 날짜를 그대로 적용해 A를 포함한다. 작성일보다 앞선 날짜 하루만 지정하면 A는 제외된다. 기간을 생략한 질문에 자동 날짜 조건을 붙이면 안 된다.

종료일이 실제 검색에 적용됐는지 보려면 A 작성일의 **전날**을 `D_PREV`로 바꿔 새 대화에서 질문한다.

> 상품 N의 D_PREV부터 D_PREV까지 답변 완료된 공개 문의에서 빵을 부드럽게 먹는 방법을 의미 검색으로 찾아줘. 문의 ID와 답변을 인용하고 적용한 기간을 알려줘.

위 예시처럼 A의 작성일이 2026-10-14라면 두 곳 모두 `2026-10-13`을 넣는다.

기대 결과: 그 기간 밖인 **문의 #I_A는 제외**된다. 답변에 요청한 기간이 적혔더라도 A를 인용하면 실패다. 최초 실제 채팅 파일럿에서는 종료일 인자를 생략한 채 요청 기간을 조회했다고 표현한 문제가 확인됐으므로, 기간 문구와 실제 반환 문의를 함께 확인한다. 다른 과거 문의가 있으면 그 문의의 작성일과 ID도 대조한다.

문의 답변 생성 중 중지를 누른 뒤 추가 출력이 멈추고 다음 질문이 가능한지 확인한다. 일부 답변을 받은 뒤 중지했다면 새로고침 후 그 부분이 복원되는지도 확인한다. Gemini 일시 장애나 시간 초과가 발생한 결과는 근거 없음 응답으로 판정하지 않고 오류 문구와 서버의 안전한 오류 코드를 기록한다.

## 6. 미답변 문의 삭제 — 마지막에 실행

일반 구매자 계정으로 공개 문의 B를 별도 작성한다.

- 제목: `삭제검증 문구: 빵 포장을 열면 부스러기가 쏟아집니다`
- 본문: `삭제검증 문구입니다. 포장을 열면 빵 부스러기가 많이 쏟아집니다.`

`I_B`를 기록하고 수동 처리 명령으로 색인을 완료한 뒤 의미 검색에서 B의 ID·인용을 확인한다. **셀러 답변은 작성하지 않는다.** 답변 완료된 A는 기존 정책상 구매자가 삭제할 수 없다.

구매자 본인의 `/my/inquiries`에서 미답변 B를 삭제한 뒤 관리자 새 대화에서 질문한다.

> 상품 N의 전체 기간 공개 문의에서 삭제검증 문구나 포장을 열 때 빵 부스러기가 쏟아진다는 내용을 의미 검색으로 찾아줘. 문의 ID와 원문을 인용해줘.

기대 결과: **삭제한 #I_B를 반환하지 않는다.** 삭제 성공 직후 원본 FK로 청크·작업이 함께 없어지므로 삭제 후 worker 명령은 필요 없다. 다른 공개 문의의 인용이 있다면 삭제한 B와 구별한다.

## 종료와 결과 기록

각 항목의 질문·답변·실제 상품/문의 ID, 처리 명령의 `version/status`, 통과 여부를 기록한다. 일반 계정과 체험 계정은 서로 다른 저장 경로이므로 한쪽 화면 검증으로 다른 쪽도 완료했다고 표시하지 않는다.

검증이 끝나면 검색 공개 플래그를 되돌리고 백엔드를 재시작한다.

```dotenv
AI_SEARCH_INQUIRIES_ENABLED=false
AI_SEARCH_WORKER_ENABLED=false
```

문의 작업 생성 플래그는 이후 작업 계획에 따라 유지할 수 있다. 전체 과거 문의의 초기 색인과 문의 최종 답변 평가·사람 대조는 별도 공개 조건이다. 리뷰 최종 답변 30개의 사람 검토도 기존 미완료 항목으로 남아 있다.

## 수동 명령이 필요한 이유와 자동 반영

위 절차에서는 색인 전후를 직접 비교하도록 `AI_SEARCH_WORKER_ENABLED=false`로 설정한다. 공개 문의 작성·판매자 답변 저장 시 원본 DB와 색인 작업을 같은 트랜잭션으로 저장하지만, 원문의 임베딩 생성과 검색 색인 저장은 별도 워커가 처리한다. 새 버전의 색인이 준비되기 전에는 이전 버전의 인용을 최신 내용으로 반환하지 않는다.

`search:inquiry:work --apply --limit=1`은 이 대기 작업을 수동으로 최대 하나 처리한다. `--apply`는 실제 처리, `--limit=1`은 처리할 작업 수의 상한이다. 검색할 때마다 실행하는 명령이 아니라 공개 문의가 추가되거나 답변이 저장되어 새 작업이 생겼을 때 사용하는 수동 처리 명령이다. 삭제는 원본과 색인·작업이 함께 제거되므로 삭제 반영에 이 명령이 필요하지 않다.

자동 반영을 사용하려면 `backend/.env`를 다음과 같이 설정하고 백엔드를 중지한 뒤 다시 실행한다.

```dotenv
AI_SEARCH_INQUIRY_INDEX_ENABLED=true
AI_SEARCH_INQUIRIES_ENABLED=true
AI_SEARCH_WORKER_ENABLED=true
```

세 값은 각각 문의 색인 작업 생성, 어시스턴트의 문의 의미 검색, 백그라운드 작업 처리를 켠다. 실행 중인 백엔드 워커가 1초 간격으로 대기 작업을 확인하며 실제 완료까지는 임베딩 API 처리 시간과 앞선 작업의 대기 시간이 필요하다. 완료된 뒤에는 수동 명령 없이 검색에 반영된다. `AI_SEARCH_REVIEW_INDEX_ENABLED=true`도 유지되어 있으면 같은 워커가 리뷰 작업도 처리한다.
