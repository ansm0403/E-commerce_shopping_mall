# Sentry 로 API 장애를 "보이게" 만든 과정 — 처음부터 끝까지

> **이 문서를 읽는 사람**: Sentry 를 처음 써 보는 사람, 백엔드는 아직 익숙하지 않은 프론트엔드 신입.
> **다루는 것**: 쇼핑몰 프론트에 Sentry 를 붙였는데 백엔드 장애를 한 건도 못 잡던 문제 → 원인을 찾은 방법 → 고친 코드 → 2026-09-29 운영에서 다시 잰 결과.
> **읽는 법**: 1장(개념)을 먼저 읽고, 2장부터는 시간 순서다. 모르는 단어는 맨 끝 [용어 사전](#9-용어-사전)에 있다.
> 코드 인용은 전부 저장소의 실제 파일에서 가져왔다. 수치는 전부 실측이고, 측정 방법을 같이 적었다.

## 1. 먼저 알아야 할 Sentry 개념 7개

### 1-1. Sentry 는 무엇인가

웹사이트가 사용자 브라우저에서 에러를 내면, 개발자는 그 사실을 모른다. 사용자 컴퓨터에서 일어난 일이기 때문이다. Sentry 는 **사용자 브라우저에서 난 에러를 개발자에게 보내 주는 서비스**다.

구조는 둘로 나뉜다.

```
[사용자 브라우저]                          [Sentry 서버 (sentry.io)]
  우리 사이트 + Sentry SDK  ── 에러 보고 ──▶  모아서 정리 → 웹 대시보드에 표시
```

- **SDK**: 우리 프론트 코드에 설치하는 라이브러리(`@sentry/nextjs`). 브라우저 안에서 에러를 감지해 보내는 역할.
- **Sentry 서버**: 받은 에러를 모아 대시보드에 보여 주는 곳. 우리는 무료(Developer) 플랜을 쓴다.

이 프로젝트의 SDK 초기화는 이 파일이다.

```ts
// frontend/src/instrumentation-client.ts
Sentry.init({
  dsn: process.env.NEXT_PUBLIC_SENTRY_DSN,   // "어느 프로젝트로 보낼지" 주소
  environment: process.env.NODE_ENV,
  tracesSampleRate: process.env.NODE_ENV === 'production' ? 0.1 : 1.0,
  integrations: [Sentry.replayIntegration()],
  replaysSessionSampleRate: 0.1,              // 일반 세션의 10% 를 화면 녹화
  replaysOnErrorSampleRate: 1.0,              // 에러가 난 세션은 100% 화면 녹화
});
```

- **DSN**: "이 에러를 Sentry 의 어느 프로젝트에 넣을지" 적힌 주소. 비밀번호가 아니라 받는 곳 주소라서 브라우저 코드에 들어가도 된다.

### 1-2. 이벤트와 이슈 — 가장 중요한 구분

- **이벤트(event)**: 에러가 **한 번** 난 기록. 사용자 A 가 새로고침할 때 한 번, B 가 열 때 한 번 → 이벤트 2개.
- **이슈(issue)**: **같은 종류의 이벤트를 묶은 폴더**. 위의 2개가 같은 원인이면 이슈 1개 안에 이벤트 2개가 들어간다.

대시보드 목록의 한 줄이 이슈이고, 그 줄의 `Events` 숫자가 그 안에 쌓인 이벤트 수다.

```
이슈: "AxiosError: Network Error  /products"   ← 목록의 한 줄
  ├ 이벤트 (03:33:50)
  ├ 이벤트 (03:34:05)
  └ 이벤트 (03:34:21)                           ← Events = 3
```

왜 중요한가: **사람은 이슈를 보고, 돈(쿼터)은 이벤트로 깎인다.** 이 문서의 중반부는 전부 이 구분 위에서 돌아간다.

### 1-3. fingerprint — 어떤 이벤트를 같은 이슈로 묶을지 정하는 이름표

Sentry 는 이벤트가 들어오면 "이게 기존 이슈 중 어느 것과 같은가"를 판단한다. 그 기준이 **fingerprint(지문)** 다. 기본값은 에러 메시지와 스택(어느 코드 줄에서 났는지)으로 자동 계산한다. 우리가 직접 지정할 수도 있다 — 5장에서 직접 지정한다.

### 1-4. 자동 수집 — SDK 가 "알아서" 잡는 에러

SDK 를 설치만 해도 아래 세 가지는 자동으로 잡힌다.

1. `window.onerror` — 코드가 실행 중에 던진 예외 중 **아무도 잡지 않은 것**
2. `window.onunhandledrejection` — Promise 가 실패했는데 **아무도 `.catch` 하지 않은 것**
3. `setTimeout`·이벤트 리스너 같은 브라우저 콜백 안에서 난 에러

공통점: **"처리되지 않은(unhandled)"** 에러만이다. 누군가 `try/catch` 나 `.catch` 로 받았다면, SDK 는 그것을 "개발자가 의도해서 처리한 흐름"으로 보고 보고하지 않는다. 이 규칙이 이 문서의 핵심 원인이다.

### 1-5. envelope — SDK 가 Sentry 로 보내는 택배 상자

SDK 는 이벤트를 하나씩 보내지 않고 **envelope(봉투)** 라는 형식에 담아 보낸다. 한 봉투에 여러 물건이 들어갈 수 있다.

```
{ 봉투 헤더 }
{"type":"event"}          ← 물건 1의 이름표: 에러 이벤트
{ ...에러 내용... }
{"type":"session"}        ← 물건 2의 이름표: 세션(사용자가 페이지를 열었다는 기록)
{ ...세션 내용... }
{"type":"replay_event"}   ← 물건 3: 화면 녹화 정보
```

줄 단위 JSON 이라 **봉투를 뜯어서 이름표(type)만 세면 "무엇이 몇 개 나갔는지" 알 수 있다.** 3장과 7장의 실험이 전부 이 방법을 쓴다.

### 1-6. 터널(tunnel) — 광고 차단기를 피하는 우회로

광고 차단기는 `sentry.io` 로 가는 요청을 막는 경우가 많다. 그래서 봉투를 **우리 사이트 주소(`/monitoring`)로 보내고, 우리 서버가 Sentry 로 대신 전달**하게 할 수 있다. 이것이 터널이다.

```js
// frontend/next.config.js
module.exports = withSentryConfig(..., {
  tunnelRoute: '/monitoring',
});
```

그래서 이 프로젝트에서 Sentry 로 나가는 요청을 찾으려면 `sentry.io` 가 아니라 `/monitoring` 을 봐야 한다.

### 1-7. 쿼터 — 무료 플랜의 한도

| 항목 | 월 한도 | 뜻 |
|---|---|---|
| 에러 이벤트 | 5,000건 | 넘으면 그 달 나머지 에러는 버려진다 |
| Session Replay | 50개 | 에러가 난 화면 녹화. 에러 1건마다 붙을 수 있다 |

한 번의 장애가 이벤트 수백 건을 보내면 며칠 만에 한도가 끝나고, **정작 다음 장애는 못 본다.** 5장의 "중복 억제"가 이것 때문이다.

## 2. 문제 — 백엔드가 죽었는데 Sentry 는 조용했다 (2026-09-16)

관측 도구가 제대로 동작하는지 보려고 운영 백엔드(EC2)를 **일부러 16분 내렸다.** 프론트(Vercel)는 그대로 살아 있었다.

| 본 것 | 결과 |
|---|---|
| 사용자 화면 | 상품 목록이 아예 안 뜸 — 완전한 장애 |
| 브라우저 콘솔 | `ERR_CONNECTION_REFUSED` 가 17건 |
| 외부 감시(UptimeRobot) | 감지함 |
| **Sentry 프론트 프로젝트** | **이슈 0건** |

사용자에게는 가장 큰 장애인데 에러 추적 도구가 아무 말도 안 했다.

**왜 이게 심각한가**: 이 프로젝트의 장애 알림은 "Sentry 이슈 → 운영 앱이 2분마다 조회 → 관리자 폰에 푸시" 경로 하나뿐이다(Sentry → Slack 연동은 유료라 없다). Sentry 가 조용하면 **폰도 조용하다.** 백엔드가 죽어도 아무도 모른다.

## 3. 원인 찾기 — 의심을 하나씩 지우고, 대조군을 세웠다

### 3-1. 먼저 의심한 것들

SDK 가 고장 났다고 먼저 의심했다. 하나씩 확인해서 지웠다.

| 의심 | 확인 방법 | 결과 |
|---|---|---|
| DSN 이 빌드에 안 들어갔나 | 배포된 페이지에서 `window.__SENTRY__` 확인 | 있음 — SDK 초기화됨 |
| 광고 차단기가 막았나 | `/monitoring` 터널로 요청이 나가는지 | 나감, 응답 200 |
| 알림 규칙 문제인가 | Slack 이 아니라 Sentry 웹의 Issues 화면을 직접 봄 | **이슈 자체가 없음** |
| 기존 이슈에 묶였나 | 기간·환경 필터를 다 풀고 봄 | 그 시간대 이벤트 없음 |

세 번째 줄이 중요하다. **"알림이 안 왔다"와 "이슈가 없다"는 다른 문제다.** 알림은 규칙·메일·Slack 어디서든 끊길 수 있다. 그래서 알림이 조용할 때는 반드시 Issues 화면을 직접 봐야 한다. 이번엔 Issues 화면도 비어 있었다 — 즉 **애초에 이벤트가 안 갔다.**

### 3-2. 대조군 실험 — "관찰"을 "증거"로 바꾸는 방법

"안 온다"는 관찰만으로는 원인을 정할 수 없다. SDK 가 고장 났을 수도 있고, 에러가 안 났을 수도 있다. 그래서 **조건만 바꾼 세 번의 실험**을 했다.

헤드리스 Chrome(화면 없이 코드로 조종하는 브라우저)으로 배포 사이트를 열고, Sentry 로 나가는 봉투를 가로채 이름표를 셌다.

| 시나리오 | 무엇을 했나 | 나간 에러 이벤트 |
|---|---|---|
| **A** | 코드에서 일부러 에러를 던짐 (아무도 안 잡음) | **1건** ✅ |
| **B** | 모든 `/api/**` 요청을 브라우저 안에서 끊음 (= 백엔드 다운 재현) | **0건** |
| **C** | 아무것도 안 함 (정상 사이트) | **0건** |

B 는 이렇게 만들었다. 서버를 실제로 끄지 않고 브라우저 안에서만 요청을 막는다.

```js
await page.route('**/api/**', route => route.abort('connectionrefused'));
```

**결과를 읽는 법**

- **A 가 1건** → SDK 는 멀쩡하다. 보낼 줄 안다.
- **B 와 C 가 똑같이 0건** → "백엔드가 통째로 죽은 상황"과 "아무 문제 없는 상황"이 Sentry 입장에서 **구분이 안 된다.**

이것이 대조군(C)이 필요한 이유다. B 만 봤다면 "0건이네, 이상하다"에서 멈췄을 것이다. C 와 나란히 놓으니 "장애 신호가 **전혀** 없다"는 결론이 나왔다. 2회 반복해도 같았다.

## 4. 원인 — "잘 처리한 에러"라서 안 보였다

API 요청이 실패하면 코드 안에서 이런 일이 일어난다.

```
① axios 요청 실패 (서버가 안 받음)
      ↓
② axios 인터셉터가 Promise.reject(error)      ← 실패한 Promise 가 생김
      ↓
③ TanStack Query 가 그 Promise 를 .catch 로 받음  ← 여기서 "처리됨"이 된다
      ↓
④ query.isError = true → 화면에 에러 UI 표시
      ↓
⑤ window.onunhandledrejection 은 발생하지 않음   ← Sentry 가 알 방법이 없다
```

1-4 에서 본 규칙 그대로다. **TanStack Query 가 에러를 받아서 화면에 잘 보여 주는 순간, 그 에러는 "처리된 에러"가 되고 SDK 의 자동 수집 대상에서 빠진다.**

역설적으로: **에러 처리를 잘 할수록 Sentry 는 조용해진다.** 이건 Sentry 의 버그가 아니다. "처리했다"는 것은 "의도한 흐름"이라는 선언이고, SDK 는 그 선언을 존중한 것이다.

그러면 해법은 하나다. **"이 에러는 처리했지만 그래도 알려야 한다"를 우리가 직접 말해 줘야 한다.**

## 5. 해결 — `reportApiError` 를 만들었다 (2026-09-20)

### 5-1. 어디에 붙였나 — axios 응답 인터셉터

모든 API 요청은 axios 클라이언트 두 개(`publicClient`, `authClient`)를 지난다. 그 **응답 인터셉터**(응답이 호출한 코드로 돌아가기 직전에 한 번 거치는 함수)에 한 줄을 넣었다.

```ts
// frontend/src/lib/axios/axios-http-client.ts
publicClient.interceptors.response.use(
  (response) => response,
  (error) => {
    reportApiError(error, 'public');   // ← 추가: Sentry 에 직접 알린다
    return Promise.reject(error);      // ← 기존 그대로: TanStack Query 가 받게 넘긴다
  }
);
```

**왜 여기인가**: 모든 API 실패가 반드시 지나가는 단 한 곳이다. 화면 컴포넌트마다 넣으면 빠뜨리는 곳이 생긴다. 그리고 에러는 그대로 넘기므로 **화면 동작은 하나도 바뀌지 않는다** — 관측만 한 겹 덧댄 것이다.

### 5-2. 무엇을 보내고 무엇을 버리나 — 판단이 가장 중요한 부분

모든 실패를 보내면 안 된다. 쿼터가 녹고, 진짜 장애가 소음에 묻힌다.

```ts
// frontend/src/lib/axios/report-api-error.ts
export function reportApiError(error: unknown, client: ApiClientName): void {
  if (!axios.isAxiosError(error)) return;                       // axios 에러가 아니면 버림
  if (axios.isCancel(error) || error.code === 'ERR_CANCELED') return;  // 취소된 요청 버림

  const status = error.response?.status;
  const isNetworkFailure = !error.response;     // 응답 자체가 없음 = 서버가 안 받음
  const isServerFailure = (status ?? 0) >= 500; // 5xx = 서버가 받았는데 터짐
  if (!isNetworkFailure && !isServerFailure) return;  // 그 외(4xx)는 버림
  ...
}
```

| 종류 | 예 | 보내나 | 이유 |
|---|---|---|---|
| 네트워크 실패 | 서버 다운, DNS 실패, 타임아웃 | ✅ | 이번 문제 그 자체 |
| 5xx | 500, 502, 503 | ✅ | 서버가 고장 났다는 신호 |
| 4xx | 401(로그인 만료), 403(권한 없음), 404, 400(입력 검증 실패) | ❌ | **설계된 흐름이다.** 401 은 토큰 갱신으로 이어지고, 400 은 폼에 에러를 보여 준다. 이걸 보내면 정상 사용만으로 쿼터가 녹는다 |
| 취소된 요청 | 페이지를 떠나며 끊긴 요청 | ❌ | 사용자가 떠난 것이지 장애가 아니다 |
| axios 가 아닌 에러 | 로그아웃 중 요청을 막으려고 우리가 던진 `Error` | ❌ | 우리 코드의 의도된 동작 |

### 5-3. fingerprint 를 직접 지정 — 엔드포인트별로 이슈 1개

```ts
Sentry.captureException(error, {
  fingerprint: ['api', client, method, path, label],
  //            'api' 'public' 'GET' '/products' 'ERR_NETWORK'
  tags: { 'api.path': path, 'api.status': label, ... },
});
```

- `path` 는 쿼리스트링을 뗀 경로다(`/products?page=2` → `/products`). 안 떼면 페이지 번호마다 다른 이슈가 생긴다.
- 결과: "`/products` 가 네트워크 실패" 는 몇 번이 나든 **이슈 1개**로 묶인다.
- `tags` 는 대시보드에서 "`api.path` 가 `/products` 인 것만" 같은 필터를 걸 때 쓴다.

### 5-4. 16건 — 적용하자마자 새 문제가 보였다

배포한 뒤 3장의 B 실험을 운영에 다시 돌렸다. **대조군 0건, API 차단 시 16건.** 이제 보이긴 하는데, 페이지 한 번 여는 데 16건이다.

왜 16건인가: 홈 화면이 `/products` 와 `/categories` 를 부르고, **TanStack Query 가 실패한 요청을 기본 3번 재시도**한다. 실패할 때마다 인터셉터를 지나므로 매번 보고된다.

이슈는 fingerprint 덕분에 2개로 잘 묶였다. 그런데 1-2 에서 본 것처럼 **쿼터는 이벤트로 깎인다.** 장애가 1시간 이어지고 사용자 100명이 새로고침하면 수천 건이다. 월 5,000건이 한 번의 장애로 끝난다.

### 5-5. 중복 억제 — 무작위가 아니라 규칙으로 줄였다

```ts
const DEDUPE_WINDOW_MS = 60_000;   // 같은 실패는 60초에 1건
const MAX_EVENTS_PER_TAB = 10;     // 탭 하나당 총 10건까지

if (sentCount >= MAX_EVENTS_PER_TAB) return;
const key = `${client}|${method}|${path}|${label}`;   // fingerprint 와 같은 기준
const previous = lastSentAt.get(key);
if (previous !== undefined && now - previous < DEDUPE_WINDOW_MS) return;
```

- **60초에 1건**: 같은 엔드포인트의 같은 실패가 연달아 와도 첫 번째만 보낸다. 재시도 3번 + 다른 쿼리 몇 개 = 16건이 **엔드포인트당 1건**이 된다.
- **탭당 10건**: 장애가 몇 시간 이어져도 한 사용자 탭이 보낼 수 있는 상한.
- 이 기록은 탭의 메모리에만 있다. 새로고침하면 초기화된다(서버에 저장하지 않는다).

**왜 무작위 샘플링(예: 10% 만 보내기)을 안 썼나** — 이것이 이 설계에서 가장 설명할 가치가 있는 판단이다.

무작위로 버리면 **새 장애의 첫 이벤트가 버려질 수 있다.** 그러면 이슈가 늦게 생기고, 폰 푸시도 늦게 온다. 이 프로젝트에서 알림 통로는 푸시 하나뿐이다. 그래서 "처음 보는 실패는 반드시 보내고, 같은 것의 반복만 버린다"는 **결정적(deterministic)** 규칙을 택했다.

### 5-6. 테스트로 고정

```ts
// frontend/src/lib/axios/report-api-error.spec.ts
it('다른 엔드포인트·상태는 각각 1건씩 나간다 — 첫 화면 16건이 2건으로 줄어든다', () => {
  for (let i = 0; i < 8; i += 1) {
    reportApiError(axiosError({ code: 'ERR_NETWORK', url: '/products?page=1&take=8' }), 'public');
    reportApiError(axiosError({ code: 'ERR_NETWORK', url: '/categories' }), 'public');
  }
  expect(capture).toHaveBeenCalledTimes(2);
});
```

그 외에 "4xx 는 안 보낸다", "60초 뒤에는 다시 보낸다", "탭당 10건 상한", "새 이슈의 첫 이벤트는 절대 안 버린다" 가 테스트로 있다. 누가 나중에 코드를 바꿔서 규칙이 깨지면 테스트가 먼저 실패한다.

단, 이건 **흉내 낸 호출**에 대한 테스트다. 운영 화면에서도 정말 2건이 되는지는 별개의 질문이었다 — 그래서 7장에서 다시 쟀다.

## 6. 전체 흐름 그림 — 장애가 폰에 닿기까지

```
[사용자 브라우저]
  홈 화면 → axios 가 /api/products 요청 → 실패
        │
        ▼ 응답 인터셉터
  reportApiError: 네트워크 실패? 5xx? → 60초·10건 규칙 통과?
        │ 통과하면
        ▼
  Sentry.captureException(fingerprint=['api','public','GET','/products','ERR_NETWORK'])
        │ envelope 에 담아
        ▼
  /monitoring (터널, Vercel)  ──▶  Sentry 서버: fingerprint 로 이슈 찾기 → 이벤트 +1, Last seen 갱신
                                          │
                                          │ 2분마다 조회 (API)
                                          ▼
                              [우리 백엔드 — 운영 앱 폴러]
                               level 이 error 인가? 쇼핑몰 프로젝트인가? 커서보다 새로운가?
                                          │ 맞으면
                                          ▼
                              Expo Push → 관리자 폰에 알림
```

폴러(poller)는 **정해진 주기마다 가서 물어보는 코드**다. Sentry 가 우리에게 알려 주는(웹훅) 방식은 유료라서, 우리가 2분마다 Sentry 에 "새 거 있어?" 하고 묻는다. 코드는 `backend/src/ops/ops-poller.service.ts` 의 `@Cron('0 */2 * * * *')` — 짝수 분 정각마다 돈다.

## 7. 운영 재측정 — 2026-09-29 에 한 일과 이유

5장의 "16건 → 2건"은 단위 테스트에만 있었다. 면접에서 "운영에서도 그런가요?"에 답하려고 같은 조건으로 다시 쟀다.

### 7-1. 측정 도구 — `scripts/probe/api-down.mjs`

3장의 B 실험을 저장소에 스크립트로 옮겼다. 하는 일은 셋이다.

1. 헤드리스 Chrome 으로 운영 홈을 연다.
2. 브라우저 안에서 `/api/**` 를 전부 끊는다 — **운영 서버는 아무 영향도 받지 않는다.** 요청이 브라우저를 떠나기 전에 끊기기 때문이다.
3. `/monitoring` 으로 나가는 봉투를 가로채 이름표를 센다.

모드가 둘이다.

| 모드 | 명령 | Sentry 로 실제 전송 | 쓰는 이유 |
|---|---|---|---|
| 차단(기본) | `node scripts/probe/api-down.mjs` | ❌ 봉투를 읽고 버린다 | 쿼터를 안 쓰고 "SDK 가 보내려 한 수"를 센다 |
| 실제 | `--allow-sentry` | ✅ 보내고 응답 코드까지 기록 | "Sentry 가 받았는지"를 확인한다 |

매 회차는 **새 탭**이다. 5-5 의 60초·10건 기록이 탭 메모리라서, 회차끼리 섞이지 않는다.

### 7-2. 단계별로 한 일과 이유

**0단계 — 차단 모드로 한 번 돌림**
- 결과: `api 차단 16회 · 에러 이벤트 2건 · 지문 2종`
- 이유: 스크립트가 동작하는지 쿼터 없이 확인. 그리고 이미 여기서 **실패한 요청 16개가 이벤트 2건으로 묶이는 것**이 운영 화면에서 보였다.

**1단계 — 측정 전 Sentry 화면 캡처**
- 결과: `Network Error` 이슈 2개, Events **14** 와 **5**.
- 이유: 09-20 에 만들어진 이슈가 남아 있으면 오늘 이벤트는 **새 이슈가 아니라 기존 이슈에 쌓인다.** 늘어난 양을 재려면 기준값이 필요하다.
- 덤으로 보인 것: 두 이슈의 추이 그래프 첫 막대가 **12 와 4**. 합이 16 — 09-20 의 "16건"이 그대로 남아 있었다. 그때도 이슈는 2개로 묶였고, 많았던 것은 이벤트 수였다는 증거다.

**2단계 — 대조군(C)을 실제 전송으로**
- 명령: `node scripts/probe/api-down.mjs --control --allow-sentry --json probe-C.json`
- 결과: 에러 이벤트 **0건**, Sentry 응답 `200, 200, 200`(세션만 나감).
- 이유: 정상 화면에서 0건이어야 B 의 숫자를 "장애 신호"로 읽을 수 있다. 3장과 같은 논리.

**3단계 — 본 측정(B) 3회, 실제 전송**
- 명령: `node scripts/probe/api-down.mjs --runs 3 --allow-sentry --json probe-B.json`
- 결과: 매 회 `api 차단 16회 · 에러 이벤트 2건(/categories, /products)`, Sentry 응답 전부 **200**. 합계 6건.
- 이유: 적용 전 측정과 **같은 조건**(API 전부 차단 + 홈 첫 화면 1회)이어야 0건과 비교할 수 있다. 3회는 우연이 아님을 보이려고.
- 200 이 중요한 이유: SDK 가 이벤트 id 를 만들었다는 것만으로는 **전송 증거가 아니다**(광고 차단기가 막아도 id 는 생긴다 — 운영 앱 연동 작업에서 겪은 함정). Sentry 서버가 200 으로 받았다는 것이 증거다.

**4단계 — 받은 쪽에서 세기**
- 결과: 두 이슈가 14 → **17**, 5 → **8**. 각각 +3, 합계 +6. **새 이슈 0개.** Last seen 은 3회차 시각과 같은 03:34:21.
- 이유: "보냈다"(스크립트)와 "받았다"(Sentry)를 따로 세야 중간에 사라진 게 없음을 말할 수 있다. 보낸 6 = 받은 6.

**5단계 — 폰 알림 시각**
- 결과: 운영 백엔드 로그 `03:36:01 푸시 발송: 이슈 2건`, 폰에 AxiosError 알림 2건.
- 이유: "장애 → Sentry → 사람"까지의 시간을 처음 잴 수 있었다.
- 마지막 이벤트(03:34:21)에서 **1분 40초**. 폴러가 짝수 분(03:34:00)에 돌았을 땐 아직 이벤트가 없어서 못 봤고, 다음 회차(03:36:00)에 잡았다. 이 구조에서 최악은 약 2분이다.

### 7-3. 결과 한 표

| 단계 | 페이지 로드당 Sentry 에러 이벤트 | 이슈 |
|---|---|---|
| 적용 전 (09-16) | **0건** | 0 |
| 적용 후, 억제 전 (09-20) | **16건** | 2 |
| 중복 억제 후 (09-29) | **2건** — 3회 반복, 보낸 6 = 받은 6 | 기존 2개에 쌓임, 새 이슈 0 |
| 대조군 (정상 화면) | 0건 | — |
| 폰 알림까지 | 마지막 이벤트 후 **1분 40초** | — |

### 7-4. 쿼터를 얼마나 썼나

| 항목 | 사용 | 한도 |
|---|---|---|
| 에러 이벤트 | 6건 | 월 5,000 |
| Session Replay | **6개** | 월 50 |

Replay 가 예상(3개)의 두 배였다. 에러가 난 세션은 100% 녹화하는 설정인데, 한 페이지에서 에러 이벤트가 2건 나가자 녹화도 2건 붙었다. **다음에 잴 때는 2회면 충분하다.**

### 7-5. 되돌린 것 — 없다

`--allow-sentry` 는 스크립트 안의 옵션이다. 운영 프론트도, Sentry 설정도, 백엔드도 건드리지 않았다. 측정이 운영 상태를 바꾸지 않았다.

## 8. 이 경험으로 설명할 수 있게 된 것

### 8-1. 배운 것 네 가지

1. **에러 추적 도구를 설치한 것과 에러가 추적되는 것은 다르다.** 설치 직후 "테스트 에러 던지기"는 통과한다 — 그건 처리되지 않은 에러 경로만 확인한 것이다.
2. **관측 도구는 대조군을 두고 검증한다.** "장애 때 0건"만 보면 원인을 못 정한다. "정상 때와 같은가"를 봐야 한다.
3. **무엇을 안 보낼지가 설계의 절반이다.** 4xx 를 버리고, 반복을 버리고, 그래도 첫 이벤트는 절대 안 버린다.
4. **이벤트와 이슈를 구분한다.** 묶음(fingerprint)과 쿼터 절약(억제)은 다른 장치이고, 캡처의 12+4=16 이 그 구분을 보여 줬다.

### 8-2. 면접에서 받을 수 있는 질문

| 질문 | 답의 뼈대 |
|---|---|
| Sentry 를 붙였는데 왜 API 장애가 안 잡혔나요? | 자동 수집은 처리되지 않은 에러만 / axios 실패를 TanStack Query 가 받으면 처리된 에러 / 대조군 B = C 로 확인 |
| 그럼 모든 API 에러를 보내면 되지 않나요? | 4xx 는 설계된 흐름이라 소음 / 무료 쿼터는 이벤트로 깎임 / 재시도 때문에 한 번의 장애가 16건 |
| 왜 샘플링을 안 썼나요? | 새 장애의 첫 이벤트를 버리면 푸시가 늦는다 / 알림 통로가 푸시 하나뿐 / 반복만 규칙으로 버림 |
| 운영에서 효과를 어떻게 확인했나요? | 같은 조건(API 차단 + 첫 화면)으로 0 → 16 → 2 / 보낸 6 = 받은 6 / 대조군 0 / 폰까지 1분 40초 |
| 어떻게 쟀나요? | 헤드리스 Chrome 이 브라우저 안에서만 API 를 끊고 Sentry 봉투를 셈(보낸 쪽) + Sentry 이슈의 Events 수(받은 쪽) + 백엔드 로그(푸시 시각) |
| 한계는요? | 폴링이라 최악 약 2분 / Replay 쿼터가 50개로 빠듯 / 탭 메모리 기준이라 사용자가 많으면 사용자 수만큼 이벤트 |

### 8-3. 이 사례로 말하면 안 되는 것

- "모든 에러를 수집한다" — 4xx 는 의도적으로 버린다.
- "이벤트 87.5% 절감" 처럼 퍼센트만 — 쓰려면 "16건 → 2건"과 함께.
- "알림 시간을 N% 단축" — 비교 대상이 없다. 1분 40초는 처음 잰 값이다.

## 9. 용어 사전

| 용어 | 뜻 |
|---|---|
| SDK | 우리 코드에 설치하는 Sentry 라이브러리. 브라우저 안에서 에러를 감지해 보낸다 |
| DSN | "어느 Sentry 프로젝트로 보낼지" 적힌 주소 |
| 이벤트 | 에러가 한 번 난 기록. 쿼터를 깎는 단위 |
| 이슈 | 같은 종류의 이벤트를 묶은 것. 대시보드 목록의 한 줄 |
| fingerprint | 어떤 이벤트를 같은 이슈로 묶을지 정하는 이름표 |
| handled / unhandled | 누군가 `catch` 로 받은 에러 / 아무도 안 받은 에러. SDK 는 unhandled 만 자동 수집 |
| envelope | SDK 가 Sentry 로 보내는 줄 단위 JSON 봉투. 이름표(type)로 내용물을 구분 |
| 터널 | 광고 차단기를 피하려고 우리 주소(`/monitoring`)로 보내고 서버가 대신 전달하는 방식 |
| Session Replay | 에러가 난 세션의 화면 녹화. 무료 월 50개 |
| 쿼터 | 무료 플랜의 월 한도. 넘으면 그 달 나머지가 버려진다 |
| 인터셉터 | axios 요청·응답이 호출한 코드에 닿기 전에 한 번 거치는 함수 |
| 대조군 | 조건 하나만 빼고 똑같이 한 실험. 차이가 그 조건 때문인지 확인하는 기준 |
| 헤드리스 Chrome | 화면 없이 코드로 조종하는 브라우저. 여기선 Playwright(`playwright-core`)로 조종 |
| `page.route` | Playwright 에서 특정 요청을 가로채 끊거나 가짜 응답을 주는 기능 |
| 폴링 / 폴러 | 정해진 주기마다 가서 새 것이 있는지 물어보는 방식 / 그 코드 |
| 웹훅 | 반대로 상대가 우리에게 알려 주는 방식. Sentry 에선 유료라 폴링을 씀 |
| 결정적 억제 | 무작위가 아니라 규칙(60초 1건)으로 버리는 것. 첫 이벤트는 항상 남는다 |
| Last seen | 그 이슈에 마지막으로 이벤트가 들어온 시각 |
