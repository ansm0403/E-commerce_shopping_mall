# Ops Companion (RN 앱) — 학습 노트

> **이 폴더는 무엇인가**
> [`docs/roadmap/ops-companion-design.md`](../../roadmap/ops-companion-design.md) 는 **설계와 결정의 기록**이다.
> Phase 별 계획, 기각된 대안, 물려받은 전제가 시간순으로 쌓여 있어 "무엇을 왜 정했는가"를 담는다.
>
> 이 폴더는 그 결과로 **실제로 짜인 코드**를, **React Native 를 처음 접한다는 가정**으로 다시 푼 것이다.
> 설계 문서가 *무엇을 하기로 했는지* 라면, 이 폴더는 *지금 저장소에 있는 코드가 어떻게 생겼고 왜 그런지* 다.

편 번호 순서대로 읽는다. 뒤 편은 앞 편에서 설명한 개념을 다시 설명하지 않는다.

## 부록 — 살아 있는 문서

| 파일 | 제목 | 성격 | 마지막 갱신 |
|---|---|---|---|
| [infra-story](./infra-story.md) | 인프라 이야기 — 우리 앱은 누구와 어떻게 일하는가 | **계속 고쳐 쓰는 문서** | 2026-09-22 (`feat/ops-source-reading`, Phase 5) |

편 번호가 붙은 노트와 성격이 다르다.

- **번호 붙은 편(1편·2편…)** 은 Phase 가 끝난 시점의 **기록**이다. 그 시점의 코드를 설명하고, 이후에는 사실이 틀어진 부분만 고친다.
- **infra-story** 는 **현재 상태의 지도**다. Metro·Expo Go·개발 빌드·EAS·Firebase/FCM·Expo Push·Sentry·nginx/EC2 가 서로 어떻게 맞물려 앱을 돌리는지를 **시간 순서(개발 → 빌드 → 조회 → 푸시)** 로 푼다. 인프라가 늘거나 연결이 바뀌면 **덧붙이지 말고 해당 장을 고쳐 쓴다.** 용어 사전도 거기 모여 있으니, 새 용어가 헷갈리면 먼저 그 문서를 본다.

1편의 장 구성은 이렇다.

- **0장**은 이 앱이 무엇이고 지금 어디까지 됐는지다. 여기만 읽어도 전체 그림은 잡힌다.
- **1장**은 React Native·Expo 용어다. 웹(React/Next.js) 경험을 기준으로 대응시켜 설명한다.
- **2~3장**이 본편이다. 파일을 하나씩 열어 "이 코드가 왜 이렇게 생겼는지"를 짚는다.
- **4장**은 로그인·목록 조회·토큰 자동 갱신 세 흐름을 그림으로 본다.
- **5~7장**은 웹과의 차이, 실제로 밟은 함정, 실행 방법이다.

<br>

## 전제

- **React 는 안다고 본다.** 컴포넌트, `useState`, `useEffect`, Context 는 설명하지 않는다.
- **React Native 는 모른다고 본다.** `View`, `StyleSheet`, SecureStore, Metro 같은 것은 처음 나올 때 설명한다.
- 백엔드 쪽(`backend/src/ops/`, `X-Client: mobile` 분기)은 이미 만들어져 운영에 배포된 상태를 전제한다.
  그 이야기는 설계 문서 §5.6·§5.1 에 있다.

## 이어 쓰는 규칙 (새 편을 쓰는 사람·모델용)

> 이 절만 읽으면 새 편을 같은 형식으로 쓸 수 있게 하는 것이 목적이다. 형식의 실례는 [1편](./01-rn-first-app.md)이다.

**언제 쓰나.** 설계 문서의 Phase 하나가 코드로 끝났을 때 한 편을 쓴다. 실기기 확인(DoD)까지 끝난 뒤가 가장 좋고, 못 했다면 0장에 "미확인"으로 적는다.

**파일.** 한 Phase 가 한 파일이다. 이름은 `NN-영문-케밥.md`(예: `02-push-and-deeplink.md`). 위 목차 표의 해당 행을 채우고 상태를 ✅ 로 바꾼다.

**독자.** RN 초보다. 앞 편에서 설명한 용어는 다시 풀지 말고 링크로 보낸다(예: "SecureStore 는 [1편 1-7](./01-rn-first-app.md#1-7-securestore)"). 이번 편에서 처음 나오는 용어만 설명한다.

**장 구성.** 1편과 같은 뼈대를 쓰되, 해당 없는 장은 뺀다.

| 장 | 내용 | 필수 |
|---|---|---|
| 0장 | 한 문장 요약 · 왜 만들었나 · **결과**(무엇이 되고, 무엇으로 검증했고, 무엇이 미확인인가를 표로) | ✅ |
| 1장 | 이번 편에서 새로 나온 용어. 웹 경험에 대응시켜 설명 | 새 용어가 있을 때 |
| 2장 | 바뀐 폴더 구조와 흐름의 지도 | 구조가 바뀌었을 때 |
| 3장 | 파일별 코드 읽기. **짧은 인용 + "왜 이렇게 짰나"** | ✅ |
| 4장 | 핵심 흐름을 mermaid `sequenceDiagram` 으로 | ✅ |
| 5장 | 웹 또는 앞 편과 달라진 점 | 있을 때 |
| 6장 | **실제로 밟은 함정** — 문서에 없던 것, 만들면서 걸린 것 | ✅ |
| 7장 | 실행 방법과 확인 체크리스트 | ✅ |
| 8장 | 다음 편 예고 | ✅ |

**정확성.**

- 인용한 코드는 반드시 실제 파일과 대조한다. 기억으로 쓰지 않는다.
- 저장소 파일 링크는 이 폴더 기준 `../../../` 로 시작한다(예: `../../../ops-companion/src/lib/api.ts`).
- 경로에 괄호가 있으면 `%28` `%29` 로 인코딩한다. 마크다운이 `app/(auth)/...` 의 `)` 에서 링크를 끊는다.
- 쓰고 나서 링크가 전부 실제 파일을 가리키는지 확인한다.
- 머리말에 **작성 시점 커밋 해시**를 적는다. 코드가 나중에 바뀌어도 어느 시점 기준인지 알 수 있게 한다.

**인프라가 늘거나 바뀌면 — [infra-story](./infra-story.md) 를 함께 고친다.** 새 편을 쓰는 것과 별개의 의무다.

- 언제: 새 외부 서비스·계정·자격증명이 생겼을 때, 기존 연결의 방향이나 경로가 바뀌었을 때, 빌드·배포 방식이 달라졌을 때, 비밀값이 하나라도 늘었을 때.
- 어디를: 그 문서 **8장 "앞으로 바뀔 것"** 표가 Phase 별로 고칠 곳을 미리 적어 두었다. 끝난 항목은 표에서 지우고 본문 해당 장에 녹인다.
- 반드시 같이 고칠 세 곳: **0-1 전체 지도**(mermaid) · **5장 비밀값 지도** · **6장 "무엇이 죽으면 무엇이 멈추나"**. 인프라가 하나 늘면 이 셋이 모두 바뀐다.
- 새 용어는 본문 첫 등장 자리에서 풀고 **용어 사전**에도 넣는다.
- 맨 끝 **갱신 기록** 표에 날짜·커밋·바뀐 내용을 한 줄 남기고, 위 부록 표의 "마지막 갱신"도 맞춘다.
- 덧붙이기가 아니라 **고쳐 쓰기**다. "Phase 2 에서 추가됨" 같은 주석을 쌓지 말고, 처음부터 그랬던 것처럼 읽히게 쓴다. 변경 이력은 갱신 기록과 git 이 맡는다.

**앞 편이 틀려지면.** 뒤 Phase 에서 코드가 바뀌어 앞 편 설명이 사실과 달라지면, 앞 편의 해당 부분을 고치고 그 절 끝에 `> 갱신(YYYY-MM-DD, 커밋): 무엇이 바뀌었나` 한 줄을 남긴다. 새 편에서 "앞 편과 달라진 점"으로도 짚는다.

**문체.** 1편과 같다. 한 문장에 한 가지, 결론 먼저, 표는 비교할 때만. 설계 문서의 결정을 옮겨 적지 말고, **코드에서 그 결정이 어떻게 보이는지**를 쓴다.
